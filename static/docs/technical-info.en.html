Discord Verified App Architecture & Privacy

Technical Documentation & Data Policy

As an officially reviewed Discord Verified App, the Chzzk Notification Bot is engineered with strict privacy protection and high-availability architecture as top priorities.

← Back to Guide

1. Security & Privacy Policy

① Zero Privileged Intents: Security by Design

Rather than merely promising privacy, the bot proves it technically by keeping every sensitive Discord permission (Privileged Gateway Intents) completely disabled (OFF).

  • Message Content Intent (OFF): The bot cannot read or monitor user chat messages. It interacts exclusively via explicit slash commands (/).
  • Server Members Intent (OFF): Access to collect or enumerate server member rosters is completely disabled.
  • Presence Intent (OFF): User online status and activity data are never tracked.
[ Placeholder for Discord Developer Portal screenshot showing all Privileged Intents disabled ]

② Slash-Commands-Only Architecture

All features follow Discord's modern interaction specification. The bot stays completely passive and only responds when a user explicitly invokes a slash command.

③ Official Discord Verification

The bot has passed Discord's security review and identity verification to earn the Verified App badge, reliably serving 10,000+ total users in compliance with Discord's data protection policies.

2. Minimal Data Storage & Governance

  • Data Minimization: Only the Discord channel ID, the streamer's 32-character unique hash ID, and nickname are stored for alert delivery. No personally identifiable information (PII) such as names, emails, or member lists is ever collected.
  • Isolated Cloud Infrastructure: All records are stored in isolated SQLite databases running on Oracle Cloud and Google Cloud Platform instances with zero public network exposure.
  • Immediate Data Erasure: When a user deletes a subscription or removes the bot from a server, all associated server data is permanently purged immediately.

3. Global Distributed Proxy & Network Reliability

Alongside privacy, a distributed network architecture maximizes notification speed and uptime.

  • Global 5-Node Distributed Proxy: Five independent nodes — Korea (GCP-Seoul, GCP-Direct), Global (Oracle Proxy 1 & 2), and Edge (Cloudflare Workers) — distribute API traffic round-robin to prevent single points of failure and HTTP 429 rate limits.
  • Massive Rotating IP Pool: Leverages ~193,536 IPv4 addresses in GCP Seoul (asia-northeast3) and ~1,524,736 Cloudflare edge IPv4 addresses to stay resilient against throttling.
  • Zero-Downtime Failover: If any node encounters a timeout or block response, requests automatically retry across healthy standby nodes so alerts are never missed.
  • Traffic Jitter: Injects 0.1s–0.3s randomized jitter between polling requests to avoid mechanical burst patterns.

4. Multi-Cloud High Availability (HA) & Data Sync

Introduced on May 1, 2026 to guarantee continuous 24/7/365 operation.

① High Availability (HA) Architecture

  • Active-Passive Failover: The primary node (GCP) and standby node (Oracle Cloud) continuously monitor each other; if the primary fails, the standby automatically promotes itself within 30 seconds.
  • Multi-Cloud Resilience: Distributing nodes across separate cloud providers ensures uninterrupted service even during a single-vendor regional outage.

② Real-Time Data Synchronization Engine

  • Query Mirroring Technology: Every database mutation (INSERT, UPDATE, DELETE) on the Master node is mirrored immediately via authenticated REST API to the Slave node, maintaining 99.9%+ consistency.
  • Boot-Time Full-Sync: Upon restart, a node fetches a complete snapshot from its peer to automatically reconcile any updates missed while offline.

③ Duplicate Alert & Interaction Collision Prevention

  • Startup Role Negotiation: On startup, each node verifies whether an active Master already exists and enters standby mode accordingly, eliminating duplicate notifications.
  • Smart Interaction Handling: Only the active Master responds to slash commands, preventing Unknown Interaction race conditions.

5. Chzzk Region-Lock (9004) Bypass & Routing

Deployed on May 3, 2026 using a dedicated Seoul Region Proxy (GCF) to resolve HTTP 500 / code 9004 errors on Korea-only streams.

  • Dedicated Seoul Relay Node: Uses Google Cloud Functions (asia-northeast3) to handle domestic requests cleanly through 193,536 Korean IPv4 endpoints.
  • Intelligent API Routing: Live status API calls prioritize the Seoul proxy for geo-restricted streams, while community API calls continue leveraging the global distributed pool.
  • Seamless Failover: Automatically falls back to the next available node if the Seoul proxy experiences transient issues.

7. Permission Justification

The invite permission integer (150528) requests only the minimum technical permissions needed to operate.

  • View Channels: Required to locate the target channel for alert delivery.
  • Send Messages & Embed Links: Required to post Chzzk live/community notifications with rich thumbnail embeds.
  • Mention Everyone: Required when server admins configure @everyone, @here, or custom role pings on alerts.
